## 1. Why Do We Need a Build Tool?

Remember what we did manually in the classpath tutorial:

```bash
# Step 1: Compile dependencies
javac -d libraries Hello.java World.java

# Step 2: Compile our code against the dependencies
javac -cp .\libraries _1_HelloWorld.java

# Step 3: Create a JAR
jar cfe myapp.jar _1_HelloWorld -C out .

# Step 4: Run
java -jar myapp.jar
```

This was fine for 3 files. Now imagine a real project:

| Challenge | Manual Approach | Problem |
|-----------|----------------|---------|
| 50+ source files | `javac file1.java file2.java file3.java ...` | Tedious, error-prone |
| 30+ external libraries | Download each JAR, put on classpath manually | Version conflicts, missing transitive deps |
| Run tests | Compile test files separately, run JUnit manually | Easy to forget, no CI integration |
| Build JAR with manifest | Write manifest, run `jar cfm ...` | Repetitive boilerplate |
| Different environments | Change paths manually for dev/prod | Fragile, not reproducible |
| Team collaboration | "Works on my machine" — different JDK, different paths | Builds are not reproducible |

**A build tool solves all of this:**
- Compiles all source files automatically (in the right order)
- Downloads dependencies from the internet (no manual JAR management)
- Runs tests automatically
- Packages your app (JAR, WAR, etc.)
- Makes builds reproducible across machines
- Integrates with CI/CD pipelines

## 2. What is Maven?

Maven is a **build automation and dependency management tool** for Java. Created by Apache in 2004, it's the most widely used Java build tool (alongside Gradle).

**Maven's philosophy: Convention over Configuration**
- You don't configure where source files go — Maven assumes `src/main/java`
- You don't configure where tests go — Maven assumes `src/test/java`
- You don't configure the output — Maven puts it in `target/`
- You only configure what's different from the defaults

**What Maven does:**

```
Your Source Code + pom.xml
         │
         ▼
┌─────────────────────────────────────────┐
│              MAVEN                        │
│                                           │
│  1. Downloads dependencies (JARs)         │
│  2. Compiles src/main/java → .class       │
│  3. Compiles src/test/java → .class       │
│  4. Runs tests                            │
│  5. Packages into JAR/WAR                 │
│  6. Installs to local repo                │
│  7. Deploys to remote repo                │
└─────────────────────────────────────────┘
         │
         ▼
   target/myapp-1.0.jar
```

## 3. How Maven Works — The Big Picture

Maven operates on three core concepts:

### 3.1 POM (Project Object Model)

Every Maven project has a `pom.xml` file — the single source of truth for your project's configuration:
- Project identity (groupId, artifactId, version)
- Dependencies (what libraries you need)
- Plugins (how to build)
- Build settings

### 3.2 Repositories

Maven downloads dependencies from repositories (like an app store for JARs):
- **Local repository** (`~/.m2/repository`) — cached on your machine
- **Central repository** (`https://repo.maven.apache.org/maven2`) — the public default
- **Remote repositories** — company-private repos (Nexus, Artifactory)

### 3.3 Build Lifecycle

A predefined sequence of phases (compile → test → package → deploy). You run a phase, and Maven executes everything before it too.

## 4. Installing Maven

### Prerequisites
- JDK installed (`java --version` works)
- `JAVA_HOME` environment variable set

### Installation

**Windows (with Chocolatey):**
```bash
choco install maven
```

**Windows (manual):**
1. Download from https://maven.apache.org/download.cgi
2. Extract to `C:\Program Files\Maven`
3. Add `C:\Program Files\Maven\bin` to `PATH`
4. Set `MAVEN_HOME=C:\Program Files\Maven`

**Linux/Mac:**
```bash
# Ubuntu/Debian
sudo apt install maven

# Mac (Homebrew)
brew install maven
```

### Verify Installation

```bash
mvn --version   # shows Maven version, Java version, and OS
```

**Output:**

## 5. Project Structure (Convention Over Configuration)

Maven expects a specific directory layout. If you follow it, you need zero configuration for basic builds:

```
my-project/
├── pom.xml                          ← project configuration (the only required file)
├── src/
│   ├── main/
│   │   ├── java/                    ← your application source code
│   │   │   └── com/
│   │   │       └── example/
│   │   │           └── App.java
│   │   └── resources/               ← config files, properties (copied to classpath)
│   │       └── application.properties
│   └── test/
│       ├── java/                    ← test source code
│       │   └── com/
│       │       └── example/
│       │           └── AppTest.java
│       └── resources/               ← test-only config files
│           └── test-data.json
└── target/                          ← build output (generated — don't commit to git)
    ├── classes/                     ← compiled .class files
    ├── test-classes/                ← compiled test .class files
    └── my-project-1.0.jar           ← final packaged artifact
```

### Generating a Project (Scaffolding)

Maven can generate this structure for you:

```bash
mvn archetype:generate \
  -DgroupId=com.example \         # your organization/package
  -DartifactId=my-project \       # project name (becomes folder name)
  -DarchetypeArtifactId=maven-archetype-quickstart \  # template: simple Java app
  -DinteractiveMode=false         # don't prompt for input
```

This creates the full directory structure with a starter `App.java` and `AppTest.java`.

## 6. The POM File (`pom.xml`)

The POM is an XML file that describes everything about your project. Here's a minimal one:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
         http://maven.apache.org/xsd/maven-4.0.0.xsd">

    <!-- POM model version (always 4.0.0) -->
    <modelVersion>4.0.0</modelVersion>

    <!-- Project coordinates — uniquely identify this project globally -->
    <groupId>com.example</groupId>          <!-- organization/domain (like a package prefix) -->
    <artifactId>hello-world</artifactId>    <!-- project name (becomes JAR filename) -->
    <version>1.0-SNAPSHOT</version>         <!-- version (SNAPSHOT = under development) -->

    <!-- What type of artifact to produce -->
    <packaging>jar</packaging>              <!-- jar (default), war, pom, ear -->

    <!-- Project metadata -->
    <name>Hello World App</name>
    <description>A simple Maven project</description>

    <!-- Compiler settings -->
    <properties>
        <maven.compiler.source>21</maven.compiler.source>    <!-- Java version for source -->
        <maven.compiler.target>21</maven.compiler.target>    <!-- Java version for bytecode -->
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <!-- External libraries this project depends on -->
    <dependencies>
        <!-- JUnit 5 for testing -->
        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <version>5.10.1</version>
            <scope>test</scope>             <!-- only needed for tests, not in final JAR -->
        </dependency>
    </dependencies>

</project>
```

### Project Coordinates (GAV)

Every artifact in Maven is identified by three coordinates:

| Coordinate | Purpose | Example |
|-----------|---------|---------|
| `groupId` | Organization/domain (reverse domain) | `com.google.code.gson` |
| `artifactId` | Project/library name | `gson` |
| `version` | Version number | `2.10.1` |

Together they form a unique address: `com.google.code.gson:gson:2.10.1`

### SNAPSHOT vs Release Versions

| Version | Meaning |
|---------|---------|
| `1.0-SNAPSHOT` | Under active development, can change at any time |
| `1.0` | Released, immutable, never changes |
| `1.0.1` | Patch release |
| `2.0-SNAPSHOT` | Next major version in development |

### Super POM (Maven's Hidden Default POM)

Every `pom.xml` implicitly inherits from Maven's built-in **Super POM**. You never see it in your project — it's baked into the Maven installation itself. It provides all the defaults so your `pom.xml` can be minimal.

**What the Super POM defines:**
- Maven Central (`https://repo.maven.apache.org/maven2`) as the default repository
- `target/` as the output directory
- `src/main/java` as the source directory
- `src/test/java` as the test directory
- `src/main/resources` and `src/test/resources` as resource directories
- Default plugin versions (compiler, surefire, jar, install, deploy, etc.)

That's why a bare-bones `pom.xml` with just GAV coordinates already knows where to find source files and where to put output — it inherits everything from the Super POM.

```
Your pom.xml (minimal):          Super POM (hidden, built into Maven):
┌─────────────────────┐          ┌──────────────────────────────────────┐
│ groupId             │          │ default repositories (Central)       │
│ artifactId          │  ← inherits from  │ default source dirs              │
│ version             │          │ default output dir (target/)         │
│ dependencies        │          │ default plugins + versions           │
└─────────────────────┘          └──────────────────────────────────────┘
```

You can view the Super POM at:
`<MAVEN_HOME>/lib/maven-model-builder-X.X.X.jar` → inside `org/apache/maven/model/pom-4.0.0.xml`

### Effective POM (The Final Merged Result)

The **Effective POM** is what Maven actually uses after merging all layers of inheritance:

```
Super POM (Maven's defaults)
    + Parent POM (if declared)
        + Your pom.xml
            + Active profiles
                ═══════════════════
                = Effective POM (final truth — what Maven actually executes)
```

View it with:

```bash
mvn help:effective-pom   # prints the complete resolved POM (typically 200+ lines)
```

This is useful for debugging — when you're confused about where a setting comes from or why a plugin version is different than expected, the effective POM shows exactly what Maven is working with.

**C# equivalent:** It's like how a `.csproj` inherits implicit defaults from the SDK (`Microsoft.NET.Sdk`) — you don't declare `<OutputPath>bin\Debug\</OutputPath>` because the SDK provides it. Running `dotnet msbuild -pp` shows the fully expanded project file, similar to the effective POM.

## 7. Maven Build Lifecycle

Maven's build process is organized into **lifecycles**, each containing an ordered sequence of **phases**. When you run a phase, Maven executes all phases before it.

### The Default Lifecycle (Most Important)

```
validate → compile → test → package → verify → install → deploy
```

| Phase | What it Does | Equivalent Manual Command |
|-------|-------------|--------------------------|
| `validate` | Checks POM is correct, all info available | — |
| `compile` | Compiles `src/main/java` → `target/classes` | `javac -d target/classes src/**/*.java` |
| `test` | Runs unit tests from `src/test/java` | `java -cp ... org.junit.runner.JUnitCore ...` |
| `package` | Creates JAR/WAR in `target/` | `jar cf target/myapp-1.0.jar -C target/classes .` |
| `verify` | Runs integration tests and checks | — |
| `install` | Copies JAR to local repo (`~/.m2/repository`) | `cp target/*.jar ~/.m2/repository/...` |
| `deploy` | Uploads JAR to remote repo (Nexus/Artifactory) | `scp` or REST API upload |

**Key insight: phases are cumulative.** If you run `mvn package`, Maven runs: validate → compile → test → package.

```bash
mvn compile    # runs: validate → compile
mvn test       # runs: validate → compile → test
mvn package    # runs: validate → compile → test → package
mvn install    # runs: validate → compile → test → package → verify → install
```

### The Clean Lifecycle

Deletes previous build output:

```bash
mvn clean   # deletes the entire target/ directory
```

Commonly combined:

```bash
mvn clean package   # delete old build, then build fresh from scratch
```

### The Site Lifecycle

Generates project documentation:

```bash
mvn site   # generates HTML reports (test results, dependencies, Javadoc)
```

### Visualizing the Lifecycle

```
You run: mvn package

Maven executes:
┌─────────────────────────────────────────────────────────────────┐
│ validate │ compile │ test-compile │ test │ package │             │
│    ✓     │    ✓    │      ✓       │  ✓   │    ✓    │   (stop)   │
└─────────────────────────────────────────────────────────────────┘

You run: mvn clean install

Maven executes:
┌───────┐ ┌─────────────────────────────────────────────────────────────────────────┐
│ clean │ │ validate │ compile │ test-compile │ test │ package │ verify │ install │   │
│   ✓   │ │    ✓     │    ✓    │      ✓       │  ✓   │    ✓    │   ✓    │    ✓    │   │
└───────┘ └─────────────────────────────────────────────────────────────────────────┘
```

## 8. Running Maven — Step by Step

Let's build a project from scratch, mirroring what we did manually in the classpath tutorial.

### Step 1: Create the Project

```bash
mvn archetype:generate \
  -DgroupId=com.example \
  -DartifactId=hello-app \
  -DarchetypeArtifactId=maven-archetype-quickstart \
  -DarchetypeVersion=1.4 \
  -DinteractiveMode=false
```

### Step 2: Examine the Generated Structure

```
hello-app/
├── pom.xml
└── src/
    ├── main/java/com/example/App.java
    └── test/java/com/example/AppTest.java
```

**Generated `App.java`:**
```java
package com.example;

public class App {
    public static void main(String[] args) {
        System.out.println("Hello World!");
    }
}
```

### Step 3: Compile

```bash
mvn compile   # compiles src/main/java → target/classes
```

**What Maven does behind the scenes (equivalent to):**
```bash
# 1. Resolves dependencies (downloads JARs if needed)
# 2. Compiles:
javac -d target/classes \
      -cp <all-dependency-jars> \
      src/main/java/com/example/App.java
```

**Output directory:**
```
target/
└── classes/
    └── com/
        └── example/
            └── App.class
```

### Step 4: Run Tests

```bash
mvn test   # compiles tests AND runs them
```

**What Maven does:**
```bash
# 1. Compile main sources (if not already done)
# 2. Compile test sources:
javac -d target/test-classes \
      -cp "target/classes;junit-5.10.1.jar" \
      src/test/java/com/example/AppTest.java
# 3. Run tests using Surefire plugin:
java -cp "target/classes;target/test-classes;junit.jar" \
     org.junit.platform.console.ConsoleLauncher ...
```

### Step 5: Package into a JAR

```bash
mvn package   # creates target/hello-app-1.0-SNAPSHOT.jar
```

**What Maven does:**
```bash
# 1. validate + compile + test (all prior phases)
# 2. Package:
jar cf target/hello-app-1.0-SNAPSHOT.jar \
    -C target/classes .
# 3. Generates META-INF/MANIFEST.MF automatically
```

### Step 6: Run the JAR

```bash
java -cp target/hello-app-1.0-SNAPSHOT.jar com.example.App
# Output: Hello World!
```

Or make it executable by adding a plugin (see [Plugins](#13-plugins) section).

### Step 7: Install to Local Repository

```bash
mvn install   # copies JAR to ~/.m2/repository/com/example/hello-app/1.0-SNAPSHOT/
```

Now other local projects can use it as a dependency:
```xml
<dependency>
    <groupId>com.example</groupId>
    <artifactId>hello-app</artifactId>
    <version>1.0-SNAPSHOT</version>
</dependency>
```

## 9. Dependencies — The Real Power of Maven

Remember the classpath tutorial where we manually downloaded and managed JARs? Maven eliminates that entirely.

### Adding a Dependency

Say you want to use Google's Gson library for JSON parsing. Instead of:
1. Going to the Gson website
2. Downloading `gson-2.10.1.jar`
3. Putting it in a `lib/` folder
4. Adding `-cp lib/gson-2.10.1.jar` to every compile and run command

You just add this to `pom.xml`:

```xml
<dependencies>
    <dependency>
        <groupId>com.google.code.gson</groupId>
        <artifactId>gson</artifactId>
        <version>2.10.1</version>
    </dependency>
</dependencies>
```

**Maven automatically:**
1. Downloads `gson-2.10.1.jar` from Maven Central
2. Stores it in `~/.m2/repository/com/google/code/gson/gson/2.10.1/`
3. Adds it to the classpath during compilation
4. Adds it to the classpath during testing
5. Includes it when building the final artifact (if needed)

### Using the Dependency in Code

```java
package com.example;

import com.google.gson.Gson;   // available because Maven added it to classpath

public class App {
    public static void main(String[] args) {
        Gson gson = new Gson();
        String json = gson.toJson(new Person("Alice", 30));
        System.out.println(json);   // {"name":"Alice","age":30}
    }
}

record Person(String name, int age) {}
```

### Finding Dependencies

Search https://search.maven.org or https://mvnrepository.com for any library. Copy the `<dependency>` block directly into your `pom.xml`.

## 10. Dependency Scopes

Not every dependency is needed at every stage. Scopes control when a dependency is available:

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.10.1</version>
    <scope>test</scope>          <!-- only available during testing -->
</dependency>
```

| Scope | Compile Classpath | Test Classpath | Runtime Classpath | Packaged in JAR/WAR | Use Case |
|-------|:-:|:-:|:-:|:-:|----------|
| `compile` (default) | ✓ | ✓ | ✓ | ✓ | Most libraries (Gson, Spring) |
| `test` | ✗ | ✓ | ✗ | ✗ | JUnit, Mockito |
| `runtime` | ✗ | ✓ | ✓ | ✓ | JDBC drivers (MySQL connector) |
| `provided` | ✓ | ✓ | ✗ | ✗ | Servlet API (server provides it) |
| `system` | ✓ | ✓ | ✗ | ✗ | Local JAR (not in any repo — avoid) |

### Examples

```xml
<!-- Default scope (compile) — needed everywhere -->
<dependency>
    <groupId>com.google.code.gson</groupId>
    <artifactId>gson</artifactId>
    <version>2.10.1</version>
    <!-- scope defaults to "compile" if omitted -->
</dependency>

<!-- Test scope — only for unit tests -->
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.10.1</version>
    <scope>test</scope>
</dependency>

<!-- Runtime scope — not needed to compile, but needed to run -->
<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <version>8.2.0</version>
    <scope>runtime</scope>
</dependency>

<!-- Provided scope — available at compile time but the server provides it at runtime -->
<dependency>
    <groupId>jakarta.servlet</groupId>
    <artifactId>jakarta.servlet-api</artifactId>
    <version>6.0.0</version>
    <scope>provided</scope>
</dependency>
```

## 11. Transitive Dependencies

When you depend on library A, and A depends on library B, Maven automatically downloads B too. You don't need to declare B yourself.

```
Your project
  └── depends on: Gson 2.10.1
        └── depends on: (nothing — Gson has no dependencies)

Your project
  └── depends on: Spring Boot Starter Web 3.2.0
        ├── depends on: Spring Web 6.1.0
        │     └── depends on: Spring Core 6.1.0
        ├── depends on: Spring Boot Starter Tomcat 3.2.0
        │     └── depends on: Tomcat Embed Core 10.1.0
        └── depends on: Jackson Databind 2.16.0
              └── depends on: Jackson Core 2.16.0
```

**You declare 1 dependency, Maven downloads 30+.** This is why Maven is powerful — it resolves the entire dependency tree.

### Viewing the Dependency Tree

```bash
mvn dependency:tree   # shows full dependency hierarchy
```

**Output (example):**
```
[INFO] com.example:hello-app:jar:1.0-SNAPSHOT
[INFO] +- com.google.code.gson:gson:jar:2.10.1:compile
[INFO] \- org.junit.jupiter:junit-jupiter:jar:5.10.1:test
[INFO]    +- org.junit.jupiter:junit-jupiter-api:jar:5.10.1:test
[INFO]    +- org.junit.jupiter:junit-jupiter-params:jar:5.10.1:test
[INFO]    \- org.junit.jupiter:junit-jupiter-engine:jar:5.10.1:test
[INFO]       \- org.junit.platform:junit-platform-engine:jar:1.10.1:test
```

### Excluding a Transitive Dependency

Sometimes a transitive dependency conflicts with another. You can exclude it:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <version>3.2.0</version>
    <exclusions>
        <exclusion>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-tomcat</artifactId>
        </exclusion>
    </exclusions>
</dependency>
```

## 12. Maven Repositories

### Where Maven Looks for Dependencies

```
1. Local Repository (~/.m2/repository)     ← checked FIRST (cache)
         │ (not found?)
         ▼
2. Maven Central (repo.maven.apache.org)   ← public default
         │ (not found?)
         ▼
3. Custom Remote Repos (if configured)     ← company-private repos
```

### Local Repository

Every JAR Maven downloads is cached locally:

```
~/.m2/repository/
├── com/
│   └── google/
│       └── code/
│           └── gson/
│               └── gson/
│                   └── 2.10.1/
│                       ├── gson-2.10.1.jar          ← the compiled library
│                       ├── gson-2.10.1.pom          ← its POM (lists its own dependencies)
│                       └── gson-2.10.1.jar.sha1     ← checksum for integrity
└── org/
    └── junit/
        └── jupiter/
            └── ...
```

### Adding a Custom Repository

There are two places you can add custom repositories:

**1. In `pom.xml` (project-level — shared with the team):**

```xml
<project>
    ...
    <repositories>
        <repository>
            <id>company-repo</id>
            <url>https://nexus.mycompany.com/repository/maven-public/</url>
        </repository>
    </repositories>
</project>
```

This is committed to version control — everyone who builds the project uses this repo.

**2. In `~/.m2/settings.xml` (user-level — personal/credentials):**

```xml
<settings>
    <profiles>
        <profile>
            <id>company</id>
            <repositories>
                <repository>
                    <id>company-repo</id>
                    <url>https://nexus.mycompany.com/repository/maven-public/</url>
                </repository>
            </repositories>
        </profile>
    </profiles>
    <activeProfiles>
        <activeProfile>company</activeProfile>
    </activeProfiles>
</settings>
```

This is for credentials or repos you don't want in source control.

**Rule of thumb:**
- Public repos that everyone needs → `pom.xml`
- Private repos with auth credentials → `settings.xml`

### Authenticating with a Company JFrog/Nexus Repository

To download private dependencies from a company repo, you need credentials. The key rule: **credentials go in `settings.xml`, never in `pom.xml`** (which is committed to git).

The `<id>` in `<server>` must match the `<id>` in your repository declaration — that's how Maven knows which credentials to use for which repo.

**`~/.m2/settings.xml`:**
```xml
<settings>
    <!-- Credentials — NEVER put these in pom.xml -->
    <servers>
        <server>
            <id>company-jfrog</id>                    <!-- must match repo id -->
            <username>your.email@company.com</username>
            <password>AKCp8...</password>             <!-- API key from JFrog UI -->
        </server>
    </servers>

    <!-- Repository defined inside a profile -->
    <profiles>
        <profile>
            <id>company</id>
            <repositories>
                <repository>
                    <id>company-jfrog</id>            <!-- matches server id above -->
                    <url>https://mycompany.jfrog.io/artifactory/maven-virtual/</url>
                    <releases><enabled>true</enabled></releases>
                    <snapshots><enabled>true</enabled></snapshots>
                </repository>
            </repositories>
        </profile>
    </profiles>

    <!-- Activate the profile by default -->
    <activeProfiles>
        <activeProfile>company</activeProfile>
    </activeProfiles>
</settings>
```

**The flow:**
1. Maven sees a dependency not in local cache (`~/.m2/repository`)
2. Checks repositories — finds `company-jfrog` (from the active profile)
3. Needs to authenticate → looks in `<servers>` for matching `<id>` = `company-jfrog`
4. Uses those credentials to download from JFrog

#### How `settings.xml` and Profiles Are Related

Profiles can be defined in both `pom.xml` and `settings.xml`, but they serve different purposes:

| Profiles in `pom.xml` | Profiles in `settings.xml` |
|----------------------|---------------------------|
| Project-level build customization | Personal/machine-level config |
| Shared with team (committed to git) | Not shared (local to your machine) |
| Different plugin configs for dev/prod | Repository URLs and credentials |
| Different dependency versions | Proxy settings |
| Resource filtering | Server authentication |

#### Why the Separation Exists

```
pom.xml (committed to git, shared with team):
├── Declares WHAT repository to use (can also be in settings.xml)
└── Never contains passwords

settings.xml (local to your machine, never committed):
├── Credentials for repositories (<servers>)
├── Repository URLs inside profiles
├── Proxy config
└── Profile activation
```

#### Encrypting Passwords

Maven supports password encryption so credentials aren't stored in plain text:

```bash
mvn --encrypt-master-password <master-password>   # run once → creates ~/.m2/settings-security.xml
mvn --encrypt-password <your-jfrog-api-key>       # outputs an encrypted string
```

Use the encrypted string in `settings.xml`:
```xml
<server>
    <id>company-jfrog</id>
    <username>your.email@company.com</username>
    <password>{encrypted-string-here}</password>    <!-- encrypted, not plain text -->
</server>
```

### Multiple Repositories (Maven Central + Company Repo)

In real projects, you typically need both:
- **Maven Central** — for public/open-source dependencies (Hibernate, Spring, Gson, etc.)
- **Company JFrog/Nexus** — for internal/private dependencies

Maven searches repositories in the order they are declared. If a dependency isn't found in the first repo, it tries the next one.

#### Option 1: Declare Both in `pom.xml` (Simple)

```xml
<repositories>
    <!-- Company repo — checked first -->
    <repository>
        <id>company-jfrog</id>
        <url>https://mycompany.jfrog.io/artifactory/maven-virtual/</url>
        <releases><enabled>true</enabled></releases>
        <snapshots><enabled>true</enabled></snapshots>
    </repository>

    <!-- Maven Central is included by default, but you can declare it explicitly -->
    <repository>
        <id>central</id>
        <url>https://repo.maven.apache.org/maven2</url>
        <releases><enabled>true</enabled></releases>
        <snapshots><enabled>false</enabled></snapshots>
    </repository>
</repositories>
```

**Resolution order:**
1. Local cache (`~/.m2/repository`) — checked first
2. `company-jfrog` — your company repo
3. `central` — Maven Central

**Note:** Maven Central is always implicitly available (from the Super POM). You only need to declare it explicitly if you want to control the search order.

#### Option 2: Virtual Repository in JFrog (Recommended for Companies)

Most companies configure JFrog to act as a **proxy/mirror** for Maven Central. A single "virtual" repository in JFrog aggregates both public and private artifacts:

```
JFrog Virtual Repository ("maven-virtual"):
├── maven-central-remote  ← proxies/caches Maven Central
├── company-releases      ← your private released artifacts
└── company-snapshots     ← your private SNAPSHOT artifacts
```

With this setup, you only need ONE repository:

```xml
<repositories>
    <repository>
        <id>company-jfrog</id>
        <url>https://mycompany.jfrog.io/artifactory/maven-virtual/</url>
    </repository>
</repositories>
```

JFrog handles the routing:
- Request for `com.google.code.gson:gson:2.10.1` → JFrog fetches from Maven Central, caches it
- Request for `com.mycompany:internal-lib:1.0` → JFrog serves from `company-releases`

**Benefits:**
- Single URL to configure
- Company controls what external deps are allowed (security)
- Caches public deps locally (faster builds, no internet needed for cached deps)
- Single set of credentials

#### Option 3: Mirror All Repos Through JFrog (`settings.xml`)

Force ALL dependency downloads through your company repo (even Maven Central):

```xml
<settings>
    <mirrors>
        <mirror>
            <id>company-jfrog</id>
            <mirrorOf>*</mirrorOf>     <!-- intercepts ALL repository requests -->
            <url>https://mycompany.jfrog.io/artifactory/maven-virtual/</url>
        </mirror>
    </mirrors>

    <servers>
        <server>
            <id>company-jfrog</id>
            <username>your.email@company.com</username>
            <password>AKCp8...</password>
        </server>
    </servers>
</settings>
```

`<mirrorOf>*</mirrorOf>` means: no matter what repository is declared in any POM, route everything through this mirror. This is common in corporate environments for security and caching.

| `mirrorOf` value | Meaning |
|-----------------|---------|
| `*` | Mirror everything (all repos) |
| `central` | Mirror only Maven Central |
| `*,!company-snapshots` | Mirror all except company-snapshots |
| `external:*` | Mirror all except localhost |

#### Full Working Example: Maven Central + Company JFrog

**`pom.xml`** (committed to git):
```xml
<project>
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.mycompany</groupId>
    <artifactId>my-service</artifactId>
    <version>1.0-SNAPSHOT</version>

    <dependencies>
        <!-- Public dep — comes from Maven Central (via JFrog proxy) -->
        <dependency>
            <groupId>org.hibernate</groupId>
            <artifactId>hibernate-core</artifactId>
            <version>6.4.1.Final</version>
        </dependency>

        <!-- Private dep — only exists in company JFrog -->
        <dependency>
            <groupId>com.mycompany</groupId>
            <artifactId>shared-utils</artifactId>
            <version>2.3.0</version>
        </dependency>
    </dependencies>

    <repositories>
        <repository>
            <id>company-jfrog</id>
            <url>https://mycompany.jfrog.io/artifactory/maven-virtual/</url>
        </repository>
    </repositories>
</project>
```

**`~/.m2/settings.xml`** (local, never committed):
```xml
<settings>
    <servers>
        <server>
            <id>company-jfrog</id>
            <username>john.doe@mycompany.com</username>
            <password>AKCp8xxxxxxxxxxxxxxx</password>
        </server>
    </servers>
</settings>
```

```bash
mvn clean install   # downloads hibernate from Central (via JFrog), shared-utils from JFrog private
```

## 13. Plugins

Plugins extend Maven's capabilities. Each lifecycle phase is bound to a plugin goal.

### Default Plugin Bindings

| Phase | Plugin | What it Does |
|-------|--------|-------------|
| `compile` | `maven-compiler-plugin` | Runs `javac` |
| `test` | `maven-surefire-plugin` | Runs JUnit tests |
| `package` | `maven-jar-plugin` | Creates JAR file |
| `install` | `maven-install-plugin` | Copies to local repo |
| `deploy` | `maven-deploy-plugin` | Uploads to remote repo |

### Configuring a Plugin

Make the JAR executable (add Main-Class to manifest):

```xml
<build>
    <plugins>
        <!-- Configure the JAR plugin to add Main-Class to manifest -->
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-jar-plugin</artifactId>
            <version>3.3.0</version>
            <configuration>
                <archive>
                    <manifest>
                        <mainClass>com.example.App</mainClass>
                    </manifest>
                </archive>
            </configuration>
        </plugin>
    </plugins>
</build>
```

Now `mvn package` creates an executable JAR:

```bash
mvn clean package
java -jar target/hello-app-1.0-SNAPSHOT.jar   # works! Main-Class is in manifest
```

### Creating a Fat JAR (Uber JAR with All Dependencies)

By default, Maven JARs don't include dependencies. Use the Shade plugin to bundle everything:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-shade-plugin</artifactId>
    <version>3.5.1</version>
    <executions>
        <execution>
            <phase>package</phase>
            <goals>
                <goal>shade</goal>
            </goals>
            <configuration>
                <transformers>
                    <transformer implementation="org.apache.maven.plugins.shade.resource.ManifestResourceTransformer">
                        <mainClass>com.example.App</mainClass>
                    </transformer>
                </transformers>
            </configuration>
        </execution>
    </executions>
</plugin>
```

```bash
mvn clean package
java -jar target/hello-app-1.0-SNAPSHOT.jar   # includes ALL dependencies inside the JAR
```

### Setting Java Version

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <version>3.12.1</version>
    <configuration>
        <source>21</source>     <!-- Java source version -->
        <target>21</target>     <!-- bytecode target version -->
    </configuration>
</plugin>
```

Or simpler (using properties):

```xml
<properties>
    <maven.compiler.source>21</maven.compiler.source>
    <maven.compiler.target>21</maven.compiler.target>
</properties>
```

## 14. Profiles

Profiles let you customize the build for different environments (dev, test, prod):

```xml
<profiles>
    <!-- Activated when you run: mvn package -Pdev -->
    <profile>
        <id>dev</id>
        <properties>
            <db.url>jdbc:mysql://localhost:3306/devdb</db.url>
        </properties>
    </profile>

    <!-- Activated when you run: mvn package -Pprod -->
    <profile>
        <id>prod</id>
        <properties>
            <db.url>jdbc:mysql://prod-server:3306/proddb</db.url>
        </properties>
    </profile>
</profiles>
```

```bash
mvn package -Pdev    # activate the "dev" profile
mvn package -Pprod   # activate the "prod" profile
```

### Referencing Properties with `${}`

Properties defined in `<properties>` (or in a profile) can be referenced anywhere in the POM using `${property.name}` syntax:

```xml
<properties>
    <java.version>21</java.version>
    <gson.version>2.10.1</gson.version>
    <app.name>hello-app</app.name>
    <db.url>jdbc:mysql://localhost:3306/mydb</db.url>
</properties>
```

Use them elsewhere in the POM:

```xml
<!-- Reference in compiler config -->
<maven.compiler.source>${java.version}</maven.compiler.source>
<maven.compiler.target>${java.version}</maven.compiler.target>

<!-- Reference in dependency version -->
<dependency>
    <groupId>com.google.code.gson</groupId>
    <artifactId>gson</artifactId>
    <version>${gson.version}</version>       <!-- resolves to 2.10.1 -->
</dependency>

<!-- Reference in build output name -->
<build>
    <finalName>${app.name}-${project.version}</finalName>  <!-- hello-app-1.0-SNAPSHOT -->
</build>
```

#### Built-in Properties (Always Available)

Maven provides several predefined variables you can reference without declaring them:

| Property | Value | Example |
|----------|-------|---------|
| `${project.version}` | Version from `<version>` | `1.0-SNAPSHOT` |
| `${project.groupId}` | Group from `<groupId>` | `com.example` |
| `${project.artifactId}` | Name from `<artifactId>` | `hello-app` |
| `${project.basedir}` | Root directory of the project | `C:\code\hello-app` |
| `${project.build.directory}` | Output directory | `target` |
| `${maven.home}` | Maven installation path | `C:\Program Files\Maven` |
| `${java.home}` | JDK path | `C:\Program Files\Java\jdk-21` |
| `${env.VARIABLE_NAME}` | Any environment variable | `${env.PATH}` |

#### Using Properties in Resource Files (Filtering)

You can inject POM properties into config files at build time:

**`src/main/resources/application.properties`:**
```properties
app.version=${project.version}
db.url=${db.url}
```

**Enable filtering in `pom.xml`:**
```xml
<build>
    <resources>
        <resource>
            <directory>src/main/resources</directory>
            <filtering>true</filtering>   <!-- replaces ${...} placeholders at build time -->
        </resource>
    </resources>
</build>
```

After `mvn compile`, the output `target/classes/application.properties` contains:
```properties
app.version=1.0-SNAPSHOT
db.url=jdbc:mysql://localhost:3306/mydb
```

**C# equivalent:** Variable substitution in `.csproj` / MSBuild uses `$(PropertyName)` syntax instead of `${property.name}`.

## 15. Multi-Module Projects

Large projects split into multiple modules (a parent POM + child modules):

```
my-company-app/
├── pom.xml                    ← parent POM (packaging = "pom")
├── common/
│   ├── pom.xml                ← module POM
│   └── src/main/java/...
├── service/
│   ├── pom.xml                ← module POM (depends on common)
│   └── src/main/java/...
└── web/
    ├── pom.xml                ← module POM (depends on service)
    └── src/main/java/...
```

**Parent POM:**
```xml
<project>
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.company</groupId>
    <artifactId>my-company-app</artifactId>
    <version>1.0-SNAPSHOT</version>
    <packaging>pom</packaging>       <!-- parent is "pom", not "jar" -->

    <modules>
        <module>common</module>
        <module>service</module>
        <module>web</module>
    </modules>
</project>
```

**Child POM (service):**
```xml
<project>
    <parent>
        <groupId>com.company</groupId>
        <artifactId>my-company-app</artifactId>
        <version>1.0-SNAPSHOT</version>
    </parent>

    <artifactId>service</artifactId>

    <dependencies>
        <dependency>
            <groupId>com.company</groupId>
            <artifactId>common</artifactId>
            <version>1.0-SNAPSHOT</version>
        </dependency>
    </dependencies>
</project>
```

```bash
# Build all modules from the parent directory
mvn clean install   # builds common → service → web (in dependency order)
```

## Comparison: Manual vs Maven

| Task | Manual (classpath tutorial) | Maven |
|------|---------------------------|-------|
| Compile | `javac -cp libs -d out *.java` | `mvn compile` |
| Manage dependencies | Download JARs manually, set `-cp` | Add to `pom.xml`, Maven downloads |
| Run tests | Compile tests separately, run manually | `mvn test` |
| Create JAR | `jar cf app.jar -C out .` | `mvn package` |
| Classpath management | `-cp "lib1.jar;lib2.jar;lib3.jar;..."` | Automatic — Maven handles it |
| Reproducible builds | "Works on my machine" | Same POM = same build everywhere |
| Transitive dependencies | Find and download each sub-dependency manually | Automatic resolution |
| CI/CD integration | Custom scripts | `mvn clean install` — one command |

## C# / .NET Equivalents

For developers coming from the .NET ecosystem, here's how Maven concepts map to their C# counterparts:

### Tools and Components

| Java / Maven | C# / .NET | Notes |
|-------------|-----------|-------|
| Maven | MSBuild + NuGet (combined) | MSBuild compiles, NuGet manages deps — Maven does both |
| Gradle | `dotnet` CLI | Alternative build tool (Gradle is more flexible, like `dotnet` CLI) |
| `pom.xml` | `.csproj` file | Project configuration and dependency declarations |
| `settings.xml` | `nuget.config` | Repository and credentials configuration |
| Maven Central | NuGet.org | The default public package repository |
| Nexus / Artifactory | Azure Artifacts / GitHub Packages | Private package hosting |
| `~/.m2/repository` | `~/.nuget/packages` | Local package cache |

### Project Structure

| Java / Maven | C# / .NET | Notes |
|-------------|-----------|-------|
| `src/main/java` | Project root (`.cs` files) | C# has no enforced directory structure |
| `src/test/java` | Separate test project (`.Tests.csproj`) | .NET uses separate projects for tests |
| `src/main/resources` | Files marked as `EmbeddedResource` or in `wwwroot` | Config files, static assets |
| `target/` | `bin/` and `obj/` | Build output directories |
| `target/classes` | `bin/Debug/net8.0/` | Compiled output |

### Coordinates and Identity

| Java / Maven | C# / .NET | Notes |
|-------------|-----------|-------|
| `groupId` | Namespace / package owner prefix | e.g., `com.google` ↔ `Google` |
| `artifactId` | Package name / assembly name | e.g., `gson` ↔ `Newtonsoft.Json` |
| `version` | Version | Same concept: `2.10.1` |
| GAV (`group:artifact:version`) | Package ID + version | `com.google.code.gson:gson:2.10.1` ↔ `Newtonsoft.Json 13.0.3` |
| `SNAPSHOT` | Pre-release suffix (`-preview`, `-rc1`) | `1.0-SNAPSHOT` ↔ `1.0.0-preview.1` |

### Build Lifecycle

| Maven Phase | .NET Equivalent | Command |
|-------------|----------------|---------|
| `validate` | `dotnet restore` (partial) | Validates project, downloads packages |
| `compile` | `dotnet build` | Compiles source code |
| `test` | `dotnet test` | Runs unit tests |
| `package` | `dotnet pack` | Creates NuGet package (`.nupkg`) |
| `install` | `dotnet nuget push` (to local feed) | Publish to local feed |
| `deploy` | `dotnet nuget push` (to remote feed) | Publish to NuGet.org or private feed |
| `clean` | `dotnet clean` | Deletes build output (`bin/`, `obj/`) |
| `mvn clean package` | `dotnet clean && dotnet build && dotnet pack` | Full rebuild |

### Dependencies

| Java / Maven | C# / .NET | Notes |
|-------------|-----------|-------|
| `<dependency>` in `pom.xml` | `<PackageReference>` in `.csproj` | Both declare external deps |
| `mvn dependency:tree` | `dotnet list package --include-transitive` | View dependency tree |
| Transitive dependencies | Transitive dependencies | Both resolve automatically |
| `<exclusions>` | Manual workarounds or `<PrivateAssets>` | Excluding transitive deps |

**Maven `pom.xml`:**
```xml
<dependency>
    <groupId>com.google.code.gson</groupId>
    <artifactId>gson</artifactId>
    <version>2.10.1</version>
</dependency>
```

**Equivalent `.csproj`:**
```xml
<PackageReference Include="Newtonsoft.Json" Version="13.0.3" />
```

### Dependency Scopes

| Maven Scope | .NET Equivalent | Meaning |
|-------------|----------------|---------|
| `compile` (default) | Default `<PackageReference>` | Available everywhere |
| `test` | Reference in test `.csproj` only | Only for test project |
| `runtime` | `<PackageReference>` with `ExcludeAssets="compile"` | Needed at runtime, not compile |
| `provided` | `<FrameworkReference>` or SDK-included | Server/runtime provides it |
| `system` | Direct DLL reference (legacy) | Avoid in both ecosystems |

### Plugins

| Maven Plugin | .NET Equivalent | Purpose |
|-------------|----------------|---------|
| `maven-compiler-plugin` | Built into `dotnet build` | Compiles source code |
| `maven-surefire-plugin` | `dotnet test` (uses xUnit/NUnit/MSTest) | Runs tests |
| `maven-jar-plugin` | Built into `dotnet build` (produces DLL) | Creates output artifact |
| `maven-shade-plugin` | `dotnet publish --self-contained` | Fat/self-contained package |
| `maven-deploy-plugin` | `dotnet nuget push` | Upload to package feed |
| `exec-maven-plugin` | `dotnet run` | Run the application |

### Packaging

| Java / Maven | C# / .NET | Notes |
|-------------|-----------|-------|
| `.jar` | `.dll` (class library) or `.exe` (app) | Compiled output |
| `.war` | Published web app folder / Docker image | Web application deployment |
| Fat JAR (uber-jar) | Self-contained publish | Single file with all dependencies |
| `MANIFEST.MF` | `.runtimeconfig.json` + `.deps.json` | Runtime metadata |
| `java -jar app.jar` | `dotnet app.dll` or `./app.exe` | Running the app |

### Multi-Module Projects

| Java / Maven | C# / .NET | Notes |
|-------------|-----------|-------|
| Parent POM | `.sln` (solution file) | Groups multiple projects |
| Child modules | Individual `.csproj` projects | Each produces a DLL/EXE |
| `<modules>` in parent POM | Projects listed in `.sln` | Defines what to build together |
| `mvn clean install` (from parent) | `dotnet build MySolution.sln` | Builds everything in order |
| Inter-module `<dependency>` | `<ProjectReference>` | One project depends on another |

### Summary

| Concept | Java Ecosystem | .NET Ecosystem |
|---------|---------------|----------------|
| Build tool | Maven / Gradle | MSBuild / `dotnet` CLI |
| Project file | `pom.xml` / `build.gradle` | `.csproj` |
| Package repository | Maven Central | NuGet.org |
| Package format | `.jar` | `.nupkg` |
| Dependency declaration | `<dependency>` block | `<PackageReference>` |
| Local cache | `~/.m2/repository` | `~/.nuget/packages` |
| Run tests | `mvn test` | `dotnet test` |
| Create package | `mvn package` | `dotnet pack` |
| Publish | `mvn deploy` | `dotnet nuget push` |
| Multi-project | Parent POM + modules | Solution (`.sln`) + projects |
