# 19. Wrapper Classes, Boxing, and Unboxing

### What Are Wrapper Classes?

Every primitive has a corresponding wrapper class — an object that "wraps" the primitive value. They exist because many Java APIs (collections, generics, streams) require objects, not primitives.

| Primitive | Wrapper Class | Size (primitive) | Size (wrapper, approx) |
|-----------|---------------|------------------|------------------------|
| `byte` | `Byte` | 1 byte | ~16 bytes |
| `short` | `Short` | 2 bytes | ~16 bytes |
| `int` | `Integer` | 4 bytes | ~16 bytes |
| `long` | `Long` | 8 bytes | ~24 bytes |
| `float` | `Float` | 4 bytes | ~16 bytes |
| `double` | `Double` | 8 bytes | ~24 bytes |
| `char` | `Character` | 2 bytes | ~16 bytes |
| `boolean` | `Boolean` | ~1 byte | ~16 bytes |

All wrapper classes are in `java.lang` (auto-imported) and are `final` and immutable.

### Why Wrapper Classes Exist

Wrapper classes exist because large parts of Java's API only work with objects, not primitives:

1. **Generics require objects.** Due to type erasure, you can't write `List<int>` — only `List<Integer>`. Collections, Streams, and any generic class/method need wrappers.

2. **Nullability.** Primitives always have a value (`int` defaults to `0`). Sometimes you need to represent "no value" — like a database column that can be `NULL`. Only `Integer` (object) can hold `null`.

3. **Object-oriented APIs.** Many Java APIs accept `Object` as a parameter. Primitives aren't objects, so they can't be passed directly to methods like `Map.put(Object key, Object value)`.

4. **Utility methods.** Wrapper classes provide useful static methods that primitives don't have — `Integer.parseInt("42")`, `Integer.toBinaryString(10)`, `Double.isNaN(x)`, `Integer.MAX_VALUE`, etc.

5. **Reflection and serialization.** Frameworks that use reflection (Spring, Hibernate, Jackson) work with `Object` types. Primitives need to be wrapped to participate.

```java
// Without wrappers, none of this would work:
List<Integer> scores = new ArrayList<>();     // generics
Map<String, Integer> map = new HashMap<>();   // Map values
Optional<Integer> maybe = Optional.of(42);    // Optional
Stream.of(1, 2, 3).map(x -> x * 2);          // autoboxed to Integer stream

// Nullability
Integer age = null;    // "age not provided" — valid
int age = null;        // ❌ impossible

// Problem: generics don't accept primitives
List<int> numbers = new ArrayList<>();       // ❌ compile error
List<Integer> numbers = new ArrayList<>();   // ✓ works

// Problem: Maps need object keys and values
Map<int, String> map = new HashMap<>();      // ❌
Map<Integer, String> map = new HashMap<>();  // ✓

// Problem: some APIs return/accept Object
Object obj = 42;          // autoboxing to Integer (Object can't hold a primitive)
```

In short — primitives are fast but limited. Wrappers bridge the gap between the primitive world and the object-oriented world that most of Java's ecosystem expects.

### Boxing (Primitive → Wrapper)

Boxing is the process of converting a primitive into its wrapper object. Before Java 5, you had to do this manually:

```java
// Manual boxing (pre-Java 5)
int x = 42;
Integer wrapped = Integer.valueOf(x);    // explicit boxing
Integer wrapped2 = new Integer(x);       // also works but deprecated since Java 9

double d = 3.14;
Double wrappedD = Double.valueOf(d);

boolean flag = true;
Boolean wrappedB = Boolean.valueOf(flag);
```

**What happens internally:** A new object is allocated on the heap with the primitive value stored inside it.

```
Stack:          Heap:
x = 42          ┌──────────────────┐
                │ Integer object   │
wrapped ──────► │ value: 42        │
                └──────────────────┘
```

### Unboxing (Wrapper → Primitive)

Unboxing extracts the primitive value from a wrapper object:

```java
// Manual unboxing (pre-Java 5)
Integer wrapped = Integer.valueOf(42);
int x = wrapped.intValue();          // explicit unboxing

Double wrappedD = Double.valueOf(3.14);
double d = wrappedD.doubleValue();

Boolean wrappedB = Boolean.valueOf(true);
boolean flag = wrappedB.booleanValue();
```

### Autoboxing (Automatic Primitive → Wrapper)

Since Java 5, the compiler automatically inserts boxing calls — you don't need to write `Integer.valueOf()` manually:

```java
// Autoboxing — compiler inserts Integer.valueOf(42) for you
Integer a = 42;              // int → Integer (automatic)
Double b = 3.14;             // double → Double (automatic)
Boolean c = true;            // boolean → Boolean (automatic)
Character d = 'A';           // char → Character (automatic)

// Works in collections too
List<Integer> numbers = new ArrayList<>();
numbers.add(10);             // autoboxing: int 10 → Integer.valueOf(10)
numbers.add(20);             // autoboxing: int 20 → Integer.valueOf(20)

// Works in method calls
public void process(Integer value) { }
process(99);                 // autoboxing: int 99 → Integer
```

**What the compiler actually generates:**
```java
// You write:
Integer a = 42;
// Compiler generates:
Integer a = Integer.valueOf(42);

// You write:
list.add(10);
// Compiler generates:
list.add(Integer.valueOf(10));
```

### Auto-Unboxing (Automatic Wrapper → Primitive)

The compiler also automatically extracts primitives from wrappers when needed:

```java
// Auto-unboxing — compiler inserts .intValue() for you
Integer wrapped = Integer.valueOf(100);
int x = wrapped;             // Integer → int (automatic)

// In arithmetic expressions
Integer a = 10;
Integer b = 20;
int sum = a + b;             // auto-unboxes both, adds, result is int

// In comparisons with primitives
Integer count = 5;
if (count > 0) {             // auto-unboxes count to int for comparison
    System.out.println("Positive");
}

// In assignments from collections
List<Integer> numbers = List.of(1, 2, 3);
int first = numbers.get(0);  // auto-unboxing: Integer → int
```

**What the compiler actually generates:**
```java
// You write:
int x = wrapped;
// Compiler generates:
int x = wrapped.intValue();

// You write:
int sum = a + b;
// Compiler generates:
int sum = a.intValue() + b.intValue();
```

### Wrapper Classes Can Hold Null — Primitives Cannot

This is one of the most important differences and a common source of `NullPointerException`:

```java
// Primitives always have a value — they cannot be null
int x;           // default: 0 (as a field)
boolean flag;    // default: false (as a field)
// int y = null;   // ❌ compile error — primitives cannot be null

// Wrappers are objects — they CAN be null
Integer a = null;       // ✓ valid
Double b = null;        // ✓ valid
Boolean c = null;       // ✓ valid
```

#### The NullPointerException Trap

When you auto-unbox a `null` wrapper, Java throws `NullPointerException`:

```java
Integer value = null;
int x = value;          // 💥 NullPointerException at runtime!
// Compiler generates: int x = value.intValue();
// Calling .intValue() on null → NPE

// Common in real code:
Map<String, Integer> scores = new HashMap<>();
int score = scores.get("Alice");  // 💥 NPE if "Alice" not in map (returns null)

// Safe approach:
Integer score = scores.get("Alice");  // keep as Integer
if (score != null) {
    int s = score;  // safe to unbox
}

// Or use getOrDefault:
int score = scores.getOrDefault("Alice", 0);  // returns 0 if absent
```

#### When Nullability Matters

```java
// Database columns that can be NULL → use wrapper
public class Employee {
    private Integer managerId;     // null means no manager (valid business case)
    private int departmentId;      // always has a value
}

// Optional method parameters
public void setAge(Integer age) {  // null means "not specified"
    if (age != null) {
        this.age = age;
    }
}

// Collections always use wrappers (which can be null elements)
List<Integer> values = new ArrayList<>();
values.add(null);           // ✓ valid — the list can contain null
values.get(0);              // returns null (Integer)
int x = values.get(0);     // 💥 NPE — auto-unboxing null
```

### `==` vs `.equals()` on Wrappers

Since wrappers are objects, `==` compares references, not values:

```java
Integer a = 200;
Integer b = 200;
a == b;           // false! — two different objects on heap
a.equals(b);      // true  — same value

// BUT: Integer caches values -128 to 127
Integer m = 100;
Integer n = 100;
m == n;           // true (same cached object) — but NEVER rely on this!

// Safe rule: ALWAYS use .equals() for wrapper comparison
```

#### Integer Cache Explained

`Integer.valueOf(x)` returns a cached instance for values -128 to 127. This is why `==` sometimes works for small numbers but fails for larger ones:

```java
// valueOf implementation (simplified):
public static Integer valueOf(int i) {
    if (i >= -128 && i <= 127)
        return IntegerCache.cache[i + 128];  // return cached instance
    return new Integer(i);                    // create new object
}

Integer a = 127;   // cached
Integer b = 127;   // same cached instance
a == b;            // true (same object)

Integer c = 128;   // NOT cached — new object
Integer d = 128;   // NOT cached — different new object
c == d;            // false (different objects)
```

### Useful Wrapper Methods

```java
// Parsing strings to primitives
int i = Integer.parseInt("42");
double d = Double.parseDouble("3.14");
boolean b = Boolean.parseBoolean("true");
long l = Long.parseLong("123456789");

// Converting primitives to strings
String s = Integer.toString(42);
String hex = Integer.toHexString(255);    // "ff"
String bin = Integer.toBinaryString(10);  // "1010"

// Constants
int max = Integer.MAX_VALUE;    // 2,147,483,647
int min = Integer.MIN_VALUE;    // -2,147,483,648
int bytes = Integer.BYTES;      // 4

// Comparison without boxing
int cmp = Integer.compare(10, 20);  // -1 (avoids creating Integer objects)
```

### Performance Considerations

Wrappers have significant overhead compared to primitives:

```java
// Bad — creates millions of Integer objects (autoboxing in loop)
Long sum = 0L;
for (long i = 0; i < 1_000_000; i++) {
    sum += i;  // auto-unbox, add, auto-box on every iteration!
}

// Good — use primitive
long sum = 0L;
for (long i = 0; i < 1_000_000; i++) {
    sum += i;  // pure primitive arithmetic, no objects created
}
```

### When to Use Primitives vs Wrappers

| Use Case | Use Primitive | Use Wrapper |
|----------|:---:|:---:|
| Local variables and loops | ✓ | |
| Method parameters (non-nullable) | ✓ | |
| Collections (`List`, `Map`, `Set`) | | ✓ |
| Nullable fields (database columns) | | ✓ |
| Generic type parameters | | ✓ |
| Performance-critical code | ✓ | |
| Signaling "no value" with `null` | | ✓ |

**C# comparison:** C# solved this with reified generics — `List<int>` works natively. Java's type erasure means `List<Integer>` compiles down to `List<Object>` at runtime, so primitives can never be used directly in generics. Project Valhalla (in development) aims to fix this with value types.
