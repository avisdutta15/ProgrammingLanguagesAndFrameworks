# 12. Virtual Threads (Project Loom)

Available since Java 21 (preview in 19-20). Virtual threads are lightweight, JVM-managed threads that are not tied 1:1 to OS threads.

```java
// Creating virtual threads
Thread vThread = Thread.ofVirtual().name("vt-1").start(() -> {
    // This runs on a virtual thread — cheap to create (few KB vs ~1MB for platform thread)
    String result = httpClient.send(request); // blocking I/O is fine!
    // JVM automatically unmounts the virtual thread from the carrier OS thread
    // and mounts another virtual thread — no OS thread blocked
});

// Virtual thread executor — creates a new virtual thread per task
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    // Submit 100,000 concurrent HTTP requests — no problem!
    List<Future<String>> futures = new ArrayList<>();
    for (int i = 0; i < 100_000; i++) {
        futures.add(executor.submit(() -> fetchUrl(urls.get(i))));
    }
    for (Future<String> f : futures) {
        process(f.get());
    }
} // auto-shutdown

// Structured concurrency (preview in Java 21+)
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<User> user = scope.fork(() -> fetchUser(id));
    Subtask<List<Order>> orders = scope.fork(() -> fetchOrders(id));

    scope.join();           // wait for both
    scope.throwIfFailed();  // propagate exceptions

    return new UserProfile(user.get(), orders.get());
}
```

**Key points:**
- Virtual threads are scheduled by the JVM on a small pool of carrier (platform) threads
- Blocking I/O automatically yields the virtual thread (no thread wasted)
- Do NOT pool virtual threads — create them liberally (they're cheap)
- Avoid `synchronized` with blocking I/O inside (pins the carrier thread) — use ReentrantLock instead
- `ThreadLocal` works but be careful with memory (millions of virtual threads × ThreadLocal = OOM)
