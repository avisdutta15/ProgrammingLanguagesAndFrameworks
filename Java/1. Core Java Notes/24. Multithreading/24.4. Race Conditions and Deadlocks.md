# 4. Race Conditions and Deadlocks

### The Problem: Race Conditions

```java
public class Counter {
    private int count = 0;

    public void increment() {
        count++; // NOT atomic: read → modify → write
    }

    public int getCount() {
        return count;
    }
}
```

If two threads call `increment()` simultaneously, both may read the same value, increment it, and write back — losing one update. This is a **race condition**.

#### Demonstrating the Race Condition

```java
public class RaceConditionDemo {
    public static void main(String[] args) throws InterruptedException {
        Counter counter = new Counter();

        // Create two threads, each incrementing 10,000 times
        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 10_000; i++) {
                counter.increment();
            }
        });

        Thread t2 = new Thread(() -> {
            for (int i = 0; i < 10_000; i++) {
                counter.increment();
            }
        });

        t1.start();   // both threads run concurrently
        t2.start();

        t1.join();    // wait for both to finish
        t2.join();

        // Expected: 20,000
        // Actual: something less (e.g., 18,732) — updates were lost!
        System.out.println("Final count: " + counter.getCount());
    }
}
```

**Why the result is wrong:** `count++` is actually three operations:
1. **Read** the current value of `count`
2. **Add** 1 to it
3. **Write** the new value back

When two threads execute simultaneously, they can interleave:

```
Thread 1:  read count (= 5)
Thread 2:  read count (= 5)       ← reads SAME value before T1 writes
Thread 1:  write count = 6
Thread 2:  write count = 6         ← overwrites T1's update! Should be 7
```

One increment is lost. Multiply this over 20,000 iterations and you lose hundreds or thousands of updates. Run it multiple times — you'll get a different (wrong) answer each time.
