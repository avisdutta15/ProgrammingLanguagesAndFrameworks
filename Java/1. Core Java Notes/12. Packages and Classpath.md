# 12. Packages and Classpath

### What is a Package?

A package is Java's mechanism for organizing classes into namespaces — like C# namespaces or file system folders. Every class belongs to a package. Packages serve three purposes:

1. **Namespace management** — avoids class name conflicts (two `List` classes can coexist in different packages)
2. **Access control** — package-private (default) visibility restricts access to classes within the same package
3. **Logical grouping** — related classes live together (`java.util`, `java.io`, `java.sql`)

### Declaring a Package

The `package` statement must be the first non-comment line in a `.java` file:

```java
package com.example.hotel;

public class Hotel {
    private String name;
    // ...
}
```

**Convention:** reverse domain name → `com.company.project.module`

### Directory Structure Must Match Package Name

This is a hard rule in Java. The file system path must mirror the package declaration:

```
src/
└── com/
    └── example/
        └── hotel/
            ├── Hotel.java          ← package com.example.hotel
            ├── HotelService.java   ← package com.example.hotel
            └── booking/
                └── Reservation.java ← package com.example.hotel.booking
```

If the directory structure doesn't match the package declaration, `javac` will compile it but `java` won't find the class at runtime → `ClassNotFoundException`.

### Import Statements

Imports let you use classes from other packages without typing the full qualified name every time:

```java
package com.example.app;

// Import a specific class
import com.example.hotel.Hotel;

// Import all classes from a package (wildcard)
import com.example.hotel.*;

// Static import — import static members directly
import static java.lang.Math.PI;
import static java.lang.Math.sqrt;

public class App {
    Hotel h = new Hotel();       // instead of com.example.hotel.Hotel
    double r = sqrt(PI);         // instead of Math.sqrt(Math.PI)
}
```

#### Import Rules

| Rule | Example |
|------|---------|
| Wildcard doesn't import sub-packages | `import com.example.*` does NOT import `com.example.hotel.*` |
| `java.lang` is auto-imported | `String`, `System`, `Math` — no import needed |
| Import conflicts require full qualification | If both `java.util.List` and `java.awt.List` are imported, use the full name |
| Static imports are for methods/constants | `import static java.util.Collections.emptyList` |
| Imports are compile-time only | They have zero runtime cost — just syntactic sugar |

#### Resolving Ambiguous Imports

```java
import java.util.*;    // has List
import java.awt.*;     // also has List

// Compiler error: "reference to List is ambiguous"
// Fix: explicitly import the one you want
import java.util.List;

// Or use the fully qualified name inline
java.awt.List awtList = new java.awt.List();
```

### The Default Package

Classes with no `package` statement go into the **default (unnamed) package**:

```java
// No package declaration
public class Scratchpad {
    // lives in the default package
}
```

**Problems with the default package:**
- Cannot be imported by classes in named packages
- Not usable in modules (Java 9+)
- Only suitable for quick throwaway scripts

### Package-Private (Default) Access

If you don't specify an access modifier, Java uses package-private access — visible only within the same package:

```java
package com.example.hotel;

class InternalHelper {           // package-private class — not visible outside this package
    void doWork() { }            // package-private method
}

public class HotelService {
    InternalHelper helper = new InternalHelper();  // ✓ same package
}
```

```java
package com.example.app;        // different package

import com.example.hotel.InternalHelper;  // ❌ compile error — not visible
```

### What is the Classpath?

The classpath tells the JVM **where to find compiled `.class` files and libraries** at compile time and runtime. It's a list of directories, JAR files, or ZIP files.

Think of it like the `PATH` environment variable, but specifically for Java classes.

#### How the JVM Resolves a Class

When you write `new com.example.hotel.Hotel()`, the JVM:

1. Takes the fully qualified class name: `com.example.hotel.Hotel`
2. Converts dots to directory separators: `com/example/hotel/Hotel.class`
3. Searches each classpath entry for that path
4. Loads the first match it finds

```
Classpath: .;lib/gson.jar;out/classes

Looking for: com.example.hotel.Hotel
Searches:
  ./com/example/hotel/Hotel.class           ← checks here first
  lib/gson.jar!/com/example/hotel/Hotel.class  ← then inside JAR
  out/classes/com/example/hotel/Hotel.class    ← then here
```

### Setting the Classpath

#### At Compile Time (`javac -cp`)

```bash
# Compile with dependencies on classpath
javac -cp lib/gson.jar:lib/slf4j.jar -d out src/com/example/app/Main.java

# On Windows use semicolons instead of colons
javac -cp "lib/gson.jar;lib/slf4j.jar" -d out src/com/example/app/Main.java
```

#### At Runtime (`java -cp`)

```bash
# Run with classpath pointing to compiled classes + libraries
java -cp "out:lib/gson.jar:lib/slf4j.jar" com.example.app.Main

# Wildcard — all JARs in a directory
java -cp "out:lib/*" com.example.app.Main
```

#### Using the `CLASSPATH` Environment Variable (Not Recommended)

```bash
export CLASSPATH=./out:./lib/*
java com.example.app.Main
```

> Avoid setting `CLASSPATH` globally — it causes conflicts between projects. Use `-cp` explicitly or let build tools (Maven/Gradle) manage it.

### Classpath vs Sourcepath

| | Classpath (`-cp`) | Sourcepath (`-sourcepath`) |
|--|-------------------|---------------------------|
| Used by | `javac` and `java` | `javac` only |
| Contains | `.class` files and JARs | `.java` source files |
| Purpose | Find compiled classes/libraries | Find source files to compile |

### Common Classpath Errors

#### `ClassNotFoundException`

Thrown at runtime when the JVM can't find a class on the classpath.

```
Error: Could not find or load main class com.example.Main
Caused by: java.lang.ClassNotFoundException: com.example.Main
```

**Common causes:**
- Forgot to include the output directory on the classpath
- Package declaration doesn't match directory structure
- Using `.\` or `.class` extension in the `java` command
- JAR not on classpath

**Fix:**
```bash
# Wrong
java com/example/Main.class
java .\com.example.Main

# Right
java -cp out com.example.Main
```

#### `NoClassDefFoundError`

The class existed at compile time but is missing at runtime:

```
Exception in thread "main" java.lang.NoClassDefFoundError: com/google/gson/Gson
```

**Cause:** You compiled against a library but forgot to include it on the runtime classpath.

```bash
# Compiled fine (gson was on cp)
javac -cp lib/gson.jar -d out src/Main.java

# Runtime — forgot gson!
java -cp out Main    # ❌ NoClassDefFoundError

# Fix — include it at runtime too
java -cp "out:lib/gson.jar" Main
```

### Compiling and Running Multi-Package Projects

#### Project Structure

```
project/
├── src/
│   └── com/
│       └── example/
│           ├── model/
│           │   └── Hotel.java
│           └── app/
│               └── Main.java
└── out/            ← compiled output
```

#### Compile

```bash
# Compile all source files, output to 'out' directory
javac -d out src/com/example/model/Hotel.java src/com/example/app/Main.java

# Or use find/wildcard to compile everything
javac -d out $(find src -name "*.java")
```

#### Run

```bash
# Run from project root with classpath pointing to output
java -cp out com.example.app.Main
```

### Creating and Using JARs

#### Create a JAR

```bash
# Package compiled classes into a JAR
jar cf hotel-service.jar -C out/ .

# Create an executable JAR (with main class specified)
jar cfe app.jar com.example.app.Main -C out/ .
```

#### Run a JAR

```bash
# Executable JAR
java -jar app.jar

# Non-executable JAR — specify main class
java -cp hotel-service.jar com.example.app.Main

# Combine your classes + library JARs
java -cp "out:lib/hotel-service.jar:lib/gson.jar" com.example.app.Main
```

#### Inspect a JAR

```bash
# List contents
jar tf hotel-service.jar

# Extract
jar xf hotel-service.jar

# View manifest
jar xf hotel-service.jar META-INF/MANIFEST.MF
```

### How Build Tools Handle All This

In real projects, you never manage the classpath manually. Build tools do it:

| Tool | How it manages classpath |
|------|--------------------------|
| Maven | Downloads dependencies to `~/.m2/repository`, constructs classpath from `pom.xml` |
| Gradle | Resolves dependencies, builds classpath per configuration (`implementation`, `testImplementation`) |
| IDE (IntelliJ) | Reads `pom.xml`/`build.gradle`, manages classpath automatically |

```xml
<!-- Maven pom.xml — declares a dependency -->
<dependency>
    <groupId>com.google.code.gson</groupId>
    <artifactId>gson</artifactId>
    <version>2.10.1</version>
</dependency>
```

```groovy
// Gradle build.gradle
dependencies {
    implementation 'com.google.code.gson:gson:2.10.1'
}
```

When you run `mvn compile` or `gradle build`, the tool resolves all dependencies, downloads them, and constructs the full classpath — so you never type `-cp` with 50 JARs manually.

### Summary Table

| Concept | What it does | C# Equivalent |
|---------|-------------|---------------|
| `package` | Organizes classes into namespaces | `namespace` |
| `import` | Shortcut to use classes without full name | `using` |
| `import static` | Import static members directly | `using static` |
| Default package | Unnamed package (no declaration) | Global namespace |
| Classpath (`-cp`) | Where JVM looks for classes/JARs | Assembly search path / NuGet |
| `jar` file | Bundled compiled classes | `.dll` |
| Package-private access | Visible only within same package | `internal` (closest equivalent) |
